NanoTab vs Request Network: Which Should You Use for AI Agent Payments?

4 November 2026 · 6 min read

Should you use NanoTab or Request Network for AI agent payments? If you want agents paying per API call automatically at request time, use NanoTab. If you need formal on-chain invoices — request, approve, pay, reconcile — especially between businesses or DAOs, use Request Network.

These two solve adjacent but different problems. Request Network (live since 2017, REQ token) is decentralized invoicing infrastructure: create a payment request on-chain, the payer approves and settles it, everything is auditable — crypto's answer to the paper invoice. NanoTab (open-source, 2026) is a per-call paywall: wrap any HTTP endpoint so agents pay USDC per request on Base via the x402 protocol, no invoice step at all. Here's the honest breakdown.

Payment model: streaming micropayments vs discrete invoices

This is the fundamental fork. NanoTab assumes the payment is the API call — a $0.03 charge fires automatically with every request, thousands of times a day, no human or approval logic involved. Request Network assumes a payable document: someone issues a request for 500 USDC, the counterparty reviews and pays it, and the chain records the whole lifecycle. One is a tollbooth; the other is a billing department.

For AI agents that distinction matters enormously. An agent calling your weather API 10,000 times a month cannot review 10,000 invoices — it needs the tollbooth. An agent (or human) settling a monthly compute bill, a freelance milestone, or a DAO contributor payout wants the invoice: line items, due dates, and an audit trail the accountant can read.

Fees: both are cheap, in different ways

Request Network charges no protocol fee at all — you pay network gas, and that's it. REQ token staking unlocks governance and some advanced features, but basic invoicing costs nothing beyond gas. On an L2 that means fractions of a cent per invoice.

NanoTab self-hosted takes 0.1% per call (a fraction of a cent on micropayments) or 2% via the managed gateway. Neither platform will be the reason a transaction is uneconomical — but note the fee applies per call for NanoTab and per invoice for Request. At 100,000 calls a month, NanoTab's 0.1% is ~$5 on $5,000 of $0.05 calls; Request isn't designed for that shape at all (100,000 on-chain invoices would drown in gas and bookkeeping).

Chains and tokens

Request Network wins on breadth: it supports many chains and tokens, so an invoice can be denominated and settled in whatever the parties hold. That flexibility is exactly what B2B billing needs — your client pays in ETH on mainnet, your contractor in USDC on Polygon, same protocol.

NanoTab is deliberately narrow: USDC on Base only, via x402. One chain, one asset, sub-second settlement, zero seller gas. If your buyers are agents holding USDC on Base (increasingly the default wallet setup), it's frictionless. If they aren't, Request's multi-chain reach is the safer bet.

Agent fit: who actually integrates?

NanoTab ships an MCP server, so any MCP-compatible agent can discover and pay for your endpoint through the standard tool-call flow — payment is invisible plumbing inside the call itself. Request Network has SDKs and APIs, and agents can create and pay invoices programmatically, but there's no MCP-native path: you're wiring it yourself, and the request→approve→pay lifecycle usually implies an approval policy or human checkpoint somewhere. That's a feature for B2B (you want the checkpoint), but friction for autonomous per-call spend.

Maturity and trust: credit where due

Honesty requires saying this plainly: Request Network has been running on mainnet since 2018, survived multiple cycles, and processes real B2B volume through its ecosystem. NanoTab went live on Base mainnet in 2026 and is early — the code is open-source and auditable, but the track record is months, not years. If your finance team asks "who else uses this," Request has the longer answer.

Verdict: different jobs, and they stack

Use NanoTab if: you're monetizing an API per call; your buyers are agents paying sub-dollar amounts at volume; you want payment embedded invisibly in the request flow; USDC on Base works for you.

Use Request Network if: you bill businesses, DAOs, or freelancers in crypto; you need invoices with line items, due dates, and audit trails; you settle across multiple chains and tokens; you want a protocol with years of mainnet history.

Use both if: you run an agent service with usage-based pricing — NanoTab for the per-call metering, Request Network for the monthly consolidated invoice your enterprise customers' finance teams demand. Tollbooth plus billing department.

Most agent businesses will eventually need both shapes: machine-speed micropayments and human-readable invoices. Start with whichever matches your first paying buyer. (As of November 2026.)
